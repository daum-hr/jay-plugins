# 되돌리기 (undo)

비개발자를 위한 복구. 사용자는 `revert`와 `restore`와 `stash`를 구분하지 않는다 —
"되돌려줘"라고 말한다. 이 스킬이 상황을 나누고, 상황마다 **가장 안전한 방법 하나만** 쓴다.

먼저 `${CLAUDE_PLUGIN_ROOT}/references/git-collab.md`를 읽는다 — 어휘(§1), 카드(§2),
안전 기준선(§5).

**이 스킬의 약속**: 되돌린 뒤에도 "없어진 것 같은 작업"이 실제로 어디에 있는지 항상
이름을 대서 알려준다. 사라졌다는 느낌을 남기지 않는 것이 핵심이다.

## Step 1: 조용히 확인

```bash
git status --porcelain 2>&1
git rev-parse --abbrev-ref HEAD 2>&1
git log --oneline -5 2>&1
git branch -r --contains HEAD 2>/dev/null    # 직전 커밋이 이미 push됐나
git stash list 2>&1
```

## Step 2: 어떤 상황인지 묻는다

사용자 말로 이미 분명하면 건너뛴다. 아니면 AskUserQuestion:

> "어떤 걸 되돌리고 싶으세요?
> ① 아직 커밋 안 한 변경 버리기
> ② 방금 한 커밋을 고치거나 무르기
> ③ 이미 팀에 push한 커밋 되돌리기
> ④ 실수로 main에 커밋했어요
> ⑤ 지금 작업을 잠깐 치워두기 (stash)
> ⑥ 잘 모르겠어요"

⑥ → `/jay-skills:status`를 먼저 돌리고 다시 묻는다.

## ① 커밋 안 한 변경 버리기

되돌릴 수 없는 작업이므로 **반드시 두 단계**로 간다.

1. 어떤 파일의 무엇이 사라지는지 한 줄씩 보여준다 (파일명 + 변경 요약).
2. 더 안전한 대안을 먼저 제시한다:

   > "버리는 대신 stash(잠깐 치워두는 서랍)에 넣어두면 나중에 그대로 꺼낼 수 있어요.
   > ① stash에 치워두기 (권장 — 되돌릴 수 있어요)
   > ② 정말 버리기 — 이 {n}개 파일의 변경이 **영구히 사라집니다**
   > ③ 그만두기"

② 를 고르면 파일을 하나씩 지정해서만 되돌린다:

```bash
git restore --source=HEAD --staged --worktree -- {파일1} {파일2}
```

`--source=HEAD --staged --worktree`를 반드시 함께 준다. 그냥 `git restore -- {파일}`은
**커밋 대기 상태(index)** 기준으로 되돌리기 때문에, 이미 커밋 대기에 올라간 변경은
남는다 — 사용자에게는 "영구히 사라집니다"라고 말해 놓고 실제로는 일부가 살아남는
어긋남이 생긴다.

폴더 전체나 `.` 같은 통짜 형태는 쓰지 않는다 — 의도하지 않은 파일까지 날아간다.

## ② 방금 한 커밋 고치기 / 무르기

`git branch -r --contains HEAD` 결과로 갈린다.

**아직 push 안 했으면** (내 컴퓨터에만 있음):

> "아직 팀에 push 안 한 커밋이라 안전하게 고칠 수 있어요.
> ① 커밋 메시지만 고치기 / 빠뜨린 파일 추가하기
> ② 커밋 자체를 무르기 (내용은 그대로 두고 커밋만 취소 — 다시 고쳐서 커밋할 수 있어요)
> ③ 그만두기"

- ① → `git commit --amend`
- ② → `git reset --soft HEAD~1` — 작업 내용은 하나도 사라지지 않고 "커밋 대기" 상태로
  돌아간다. 이 점을 반드시 말한다.

**이미 push했으면**: 고치지 않는다. 이유를 설명하고 ③으로 넘긴다.

> "이 커밋은 이미 팀 저장소에 올라가서 동료 컴퓨터에도 갔을 수 있어요. 그래서 이력을
> 고치는 대신, revert(**반대 내용의 새 커밋**을 만들어 원상복구하는 것)로 되돌립니다.
> 기록이 남아서 나중에 무슨 일이 있었는지 알 수 있어요."

## ③ 이미 push한 커밋 되돌리기

**먼저 되돌릴 내용을 보여준다.** 어느 쪽 경로로 가든 이건 공통이다 — 그 커밋이 무엇을
바꿨는지(before/after)를 쉬운 말로 요약해서 확인받는다. revert는 "이력을 지우는 게 아니라
**반대 내용의 새 커밋**을 하나 더 만드는 것"이라는 설명도 함께 한다.

```bash
git rev-parse --abbrev-ref HEAD           # 지금 브랜치
git branch -r --contains {커밋}            # 그 커밋이 팀 저장소의 어디에 있나
```

**여기서부터는 커밋이 어디 있느냐로만 갈린다. 절차를 즉석에서 새로 만들지 않는다.**
(실측에서 이 스킬에 없는 브랜치+PR 절차를 그 자리에서 지어내 선택지로 내밀었고, 사용자는
무슨 말인지 알 수 없어 "그만둘래요"를 골랐다. 되돌리기는 결국 실행되지 않았다.)

### (a) 지금 브랜치에 있는 커밋일 때 — 그 자리에서 되돌린다

브랜치를 새로 만들지 않고, PR도 만들지 않는다.

```bash
git revert {커밋}
```

한 번에 하나씩만 한다. 충돌이 나면 `/jay-skills:fix-conflict`. 끝나면 "되돌린 내용도
팀에 알려야 해요" 하고 `/jay-skills:push`를 권한다.

### (b) main에 있는 커밋일 때 — 확인 요청(PR)으로 올린다

main에는 직접 push하지 않는다(`git-collab.md` §5). 그렇다고 사용자에게 브랜치·PR 절차를
설명하고 고르라고 하지 않는다 — **복잡한 부분은 도구가 흡수한다.**

질문에는 **무엇이 되돌려지는지만** 담는다. "별도 브랜치를 만들어서 거기에 revert 커밋을
올린 다음 PR을…" 같은 절차 설명을 선택지 문구에 넣지 않는다.

> "`{커밋 한 줄 설명}` 을 되돌립니다. main은 팀 최종본이라 바로 고치지 않고,
> **되돌리는 내용을 확인 요청(PR)으로 올려드릴게요** — 준비는 제가 다 합니다.
> ① 이대로 진행 (권장)
> ② 그만두기"

① 을 고르면 아래를 **한 흐름으로** 진행하고, 중간에 사용자를 세우지 않는다:

```bash
git switch -c revert/{되돌리는-내용-영문-이름}   # 지금 위치에서 브랜치만 생성
git revert {커밋}
```

- 브랜치 이름은 영문 소문자·하이픈으로 짓는다 (`git-collab.md` §6).
- revert에서 충돌이 나면 `/jay-skills:fix-conflict`로 넘긴다.
- push와 PR 생성은 **직접 명령을 쓰지 않고** `/jay-skills:push` → `/jay-skills:pr` 로
  이어서 진행한다. 그 스킬들이 실패 처리·확인 문구를 이미 갖고 있다 — 여기에 다시
  적으면 두 곳이 어긋난다.

끝나면 어디에 무엇이 있는지 한 줄로 말한다: "되돌리는 내용은 `revert/{이름}` 브랜치에
있고, 확인 요청 {URL} 으로 올라갔어요. 동료가 확인해서 합치면 main에 반영됩니다."

## ④ 실수로 main에 커밋했을 때

**아직 push 안 했으면** (대부분의 경우):

1. 먼저 작업을 안전한 곳에 담는다 — `git branch {feature/영문-이름}` (지금 위치에서
   브랜치만 만드는 것이라 아무것도 움직이지 않는다. 이름은 영문 소문자·하이픈 —
   `git-collab.md` §6).
2. 그 브랜치에 커밋이 들어갔는지 확인한 뒤에만 main을 정리한다:
   `git reset --keep origin/main`. `--keep`은 커밋 안 된 변경이 있으면 스스로 거부한다 —
   거부하면 그대로 두고 알린다.
3. 팀 저장소 주소를 모르거나 `origin/main`이 없으면 **정리하지 않는다**:
   "작업은 새 브랜치 `{이름}`에 안전하게 있어요. main 정리는 팀과 함께 보는 게
   좋겠습니다."

**이미 main에 push됐으면**: 이력을 손대지 않는다. ③ (b) 경로로 간다 — revert 커밋을
확인 요청(PR)으로 올린다. **즉시 팀에 알리도록 안내한다** — 동료가 이미 받아갔을 수 있다.

## ⑤ 잠깐 치워두기 (stash)

stash(지금 작업을 잠깐 치워뒀다가 나중에 그대로 꺼내는 서랍)를 쓴다.

```bash
git stash push -m "{사용자 말로 만든 한 줄 설명}"
```

**치운 뒤에는 해당 파일을 실제로 읽어서 보여준다.** `git stash list` 같은 git 쪽 기록만
보고 "치워졌어요"라고 단언하지 않는다 — 사용자가 확인하고 싶은 것은 "내가 쓴 그 줄이
지금 화면에서 사라졌나"이지 git이 뭐라고 하는지가 아니다.

> "치워뒀어요: '{설명}'. `{파일}` 에서 `{그 줄}` 이 지금은 없는 상태예요 — 방금 파일을
> 열어서 확인했습니다. 나중에 '치워둔 거 꺼내줘'라고 하시면 그대로 돌아옵니다.
> 컴퓨터를 껐다 켜도 남아 있어요."

꺼낼 때는 `git stash pop`, 충돌 나면 `/jay-skills:fix-conflict`. **꺼낸 뒤에도 마찬가지로
파일을 읽어서** 그 줄이 돌아왔음을 보여준다.

## 마무리 카드

`git-collab.md` §2 형식으로 끝내되, **"없어진 것처럼 보이는 작업이 지금 어디 있는지"를
반드시 한 줄로 명시한다**. 이 스킬에서 마무리 카드는 **생략하지 않는다** — 그 한 줄이
여기에만 실린다. 예: "되돌린 작업은 `feature/notice-list` 브랜치에 그대로 있어요" /
"치워둔 작업은 stash에 '표 정렬 작업 중'이라는 이름으로 있어요".

## 절대 하지 않는 것

- `git reset --hard`, `git clean -f` — 커밋 안 된 작업이 말없이 사라진다.
- force push.
- 이미 push한 커밋에 amend / rebase.
- 브랜치 삭제, stash 비우기(`stash drop` / `stash clear`).
- 스킬에 없는 절차를 그 자리에서 지어내 선택지로 내밀기 (③ 참조).
- 파일 지정 없는 통짜 `restore` / `checkout .`.
- 되돌릴 수 없는 작업을 확인 없이 실행하기.
