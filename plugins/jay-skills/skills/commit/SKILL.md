# 커밋하기 (commit)

비개발자를 위한 기록 도구. 기술적인 선택은 하나도 하지 않아도 된다 — 메시지는 자동으로
만든다.

커밋(작업에 이름표를 붙여 내 컴퓨터에 기록하는 것)은 **내 컴퓨터까지만** 간다. 팀에
보내는 것은 push이고, 그건 `/jay-skills:push`가 따로 한다.

## Usage
```
/jay-skills:commit
```

## 이 스킬이 하는 일

1. **무엇이 바뀌었는지 확인**한다.
2. **종류를 자동으로 고른다** (사용자에게 묻지 않는다).
3. **한 줄 메시지를 쓴다.**
4. **큰 변경이면 기록 노트도 함께** 남긴다.
5. **메시지를 보여주고 커밋**한다.
6. **내 컴퓨터에만 기록됐다는 것을 알린다** — 팀 공유는 별도 요청.

## Process

### Step 1: 변경 확인 (조용히)

```bash
git status --short
git diff --staged --stat
git diff --staged
```

아직 커밋 대기 상태(index)에 올라간 게 없으면 변경된 파일 전체를 올린다(`git add -A`) —
사용자가 "커밋해줘"라고 한 것은 지금까지의 작업 전부를 뜻한다. 단 올리기 전에 어떤
파일들인지 한 줄로 보여준다.

### Step 2: 종류·범위 자동 선택

간단한 기준으로 정한다 — **묻지 않는다.**

- 새 기능·새 화면 → `feat:`
- 고장 난 것 고치기 → `fix:`
- 문서·설명 작성 → `docs:`
- 정리·설정 변경·자잘한 유지보수 → `chore:`
- 보기(디자인·문구)만 바뀜 → `style:`

어느 영역인지 분명하면 괄호로 덧붙인다: `feat(notice):`. 애매하면 괄호 없이 쓴다.
**판단이 안 서면 `chore:`로 두고 넘어간다 — 질문으로 사용자를 붙잡지 않는다.**

### Step 3: 메시지 만들기

형식: `<종류>(<영역>): <한 줄 설명>`

예:
- `feat: 공지사항 목록 화면 추가`
- `fix(login): 로그인 후 화면이 안 넘어가던 문제 수정`
- `docs: 사용 안내 문서 작성`

한국어·영어 모두 괜찮다 — 프로젝트에서 쓰는 쪽에 맞춘다. 60자 이내로 짧게.

### Step 3.5: 큰 변경이면 기록 노트도 함께 (`/jay-skills:record` 인라인 실행)

커밋하기 **전에**, 이 변경이 기록을 남길 만한지 확인한다.

**판단 기준**: `${CLAUDE_PLUGIN_ROOT}/skills/record/SKILL.md` 의 "When to Record" 목록을
읽어서 적용한다. 그 파일이 정본이므로 여기에 옮겨 적지 않는다 (옮겨 적으면 나중에 서로
어긋난다). 프로젝트에 자체 `record` 스킬이 있으면 그쪽 목록을 쓴다.

해당하지 않으면(오타 수정, 색 하나 변경 같은 작은 일) 이 단계를 건너뛰고 Step 4로 간다.

**해당하면**:

1. 그 파일의 Step 1~3을 여기서 그대로 수행해 `docs/memories/YYYY-MM-DD_제목.md`를 쓴다.
   - **맥락은 Step 1에서 본 커밋 대기 내용**(`git diff --staged`)과 지금 대화에서 가져온다.
     `record` 안에 있는 `git diff --name-only HEAD~1`은 **돌리지 않는다** — 그 명령은
     커밋이 끝난 뒤에 쓰라고 쓰인 것이라, 지금 실행하면 *이번* 변경이 아니라 *직전*
     변경을 설명하게 된다.
2. 기록 파일도 같은 커밋에 포함한다: `git add docs/memories/{파일명}`
3. Step 4로 간다.

**기록할지 사용자에게 묻지 않는다** — 커밋은 "여러 단계 질문을 하지 않는" 도구이고,
기록은 대화와 변경 내용에서 알아서 채우는 부산물이다.

### Step 4: 보여주고, 커밋하고, 알리기

메시지를 한 문장으로 보여준 뒤:

```bash
git commit -m "<만든 메시지>"
```

성공하면 쉬운 한국어로 알린다. **세 가지가 모두 들어가야 한다**:

1. 커밋 메시지 한 줄
2. 기록 노트를 썼다면 그 파일명
3. **내 컴퓨터에만 기록됐다는 안내**

예:

> 커밋했어요!
> `feat: 공지사항 목록 화면 추가`
> 기록도 함께 남겼어요: `docs/memories/2026-04-27_notice-list.md`
> 이번 변경은 *내 컴퓨터에만* 기록됐어요. 팀과 공유하려면 `/jay-skills:push` 를
> 실행하거나 "올려줘"라고 말씀해 주세요. (저 혼자 팀 저장소에 push하지 않습니다.)

이 안내문에 **브랜치 이름을 넣지 않는다.** 안전의 축은 하나여야 한다 —
내 컴퓨터 ↔ 팀 저장소. 브랜치 이야기는 `/jay-skills:push`가 필요할 때만 꺼낸다.

기록 노트를 안 썼을 때도 3번 안내는 반드시 넣는다 — 커밋했다고 공유된 걸로 오해하면
안 된다.

### Step 5: 검사에 걸렸을 때 (쉬운 말로)

커밋 전 검사(hook)에 막히면 **원문 로그를 그대로 쏟아내지 않는다.** 옮겨서 말한다:

> "커밋이 잠시 멈췄어요. 보안 검사에서 비밀번호처럼 보이는 글자를 발견한 것 같습니다.
> 다음 중 하나를 해보세요.
> 1. 해당 파일에서 비밀번호·토큰을 지우고 다시 시도
> 2. 팀에 도움 요청 (이 파일을 최근에 고친 동료가 알 수 있어요)"

**검사를 건너뛰지 않는다** (`--no-verify` 금지).

## Rules

- 합리적인 기본값으로 정한다 — 여러 단계 질문을 하지 않는다.
- 메시지는 60자 이내.
- 큰 변경이면 기록 노트를 자동으로 남긴다 (Step 3.5). 오타 수정 같은 건 건너뛴다.
- 커밋은 내 컴퓨터까지라는 안내를 항상 넣는다 (Step 4의 3번).
- 검사 실패는 쉬운 말로 옮기고 다음 행동을 제안한다.
- push는 하지 않는다 — 사용자가 따로 요청할 때 `/jay-skills:push`가 한다.
- **이 스킬은 사용자가 커밋을 요청했을 때만 실행된다.** 다른 스킬이나 마무리 요청이
  대신 불러서 말없이 커밋하지 않는다 (`git-collab.md` §5).
