# git 협업 공용 참조 (jay-skills)

git 계열 스킬(`status` `github-login` `push` `pull` `fix-conflict` `undo` `pr`)이
공유하는 어휘·마무리 카드·에러 번역표·안전 기준선. 각 스킬은 이 표들을 복사하지 말고
필요할 때 이 파일을 읽는다 (경로: `${CLAUDE_PLUGIN_ROOT}/references/git-collab.md`,
= 플러그인 루트의 `references/git-collab.md`).

---

## 0. 이 도구들이 가정하는 팀

**개발자가 없는 팀을 가정한다.** 사용자도, 함께 일하는 동료도 비개발자다. 그래서
"개발팀이 검토해서 합쳐준다" 같은 흐름은 없다 — **확인도 합치기도 팀이 직접 한다.**

여기서 나오는 결과가 두 가지다.

1. **막혔을 때 넘길 상대가 기본적으로 "팀"이다.** "개발자에게 물어보세요"라고 말하지
   않는다. 대신 (a) 지금 상태를 그대로 두고 멈추기, (b) 그 파일을 최근에 고친 동료에게
   물어보기(`git log -1 --format='%an' -- {파일}` 로 누구인지 알 수 있다), (c) 저장소를
   만든 사람에게 문의 — 셋 중 상황에 맞는 것을 제안한다.
2. **합치기(merge)를 막아두지 않는다.** 아무도 합쳐주지 않으면 요청만 쌓이고 일이
   진행되지 않는다. 다만 합치기는 팀 최종본을 바꾸는 일이라, 충돌이 없고 사용자가 명시로
   확인했을 때만 한다 (`pr` 스킬 Step 6).

예외 — 진짜로 기술자가 필요한 자리는 그대로 남긴다: SSH 설정처럼 누군가 세팅해 준 것,
회사 자체 GitHub 서버 주소, 저장소 권한 부여. 이때도 "개발자"가 아니라 **"그 설정을 해준
사람" / "저장소를 만든 사람"**이라고 부른다.

## 1. 어휘표 — 사용자에게 말할 때 쓰는 표현

| 용어 | 사용자에게 이렇게 말한다 |
|---|---|
| commit | 저장 — 지금까지 작업을 이름표 붙여 내 컴퓨터에 보관하는 것 |
| push | 올리기 — 내 컴퓨터의 저장을 팀 저장소로 보내 동료가 볼 수 있게 하는 것 |
| pull | 받아오기 — 동료들이 팀 저장소에 올린 작업을 내 컴퓨터로 가져오는 것 |
| fetch | 목록만 확인 — 받아오기 전에 "새 게 있나"만 살펴보는 것 (보통 사용자에게 안 보임) |
| branch | 갈래 — 다른 사람 작업을 건드리지 않고 내 작업만 따로 담아두는 공간 |
| main | 모두가 함께 쓰는 갈래 — 팀의 최종본. 여기에 바로 올리지 않고, 확인을 거쳐 합친다 |
| remote / origin | 팀 저장소 — 회사 GitHub에 있는 공용 보관소. 별명이 `origin` |
| upstream | 짝 — 내 갈래가 팀 저장소의 어느 갈래와 이어져 있는지 |
| merge | 합치기 — 두 갈래의 작업을 하나로 모으는 것 |
| conflict | 충돌 — 같은 파일 같은 부분을 나와 동료가 다르게 고쳐서, 어느 쪽을 남길지 사람이 정해야 하는 상태. **고장이 아니다** |
| PR (Pull Request) | 합치기 요청 — "내 작업을 팀 최종본에 합쳐도 될까요"라고 동료에게 올리는 확인 요청 |
| stash | 보관함 — 지금 작업을 잠깐 치워뒀다가 나중에 그대로 꺼내는 서랍 |
| revert | 되돌리기 — 이전 저장을 지우는 게 아니라, 반대 내용의 새 저장을 만들어 원상복구하는 것 |
| clone | 내려받기 — 팀 저장소를 이력까지 통째로 복사해 오는 것 (zip 다운로드와 다르다) |
| force push | 덮어쓰기 — 팀 저장소의 이력을 강제로 갈아치우는 것. **절대 하지 않는다** |

**말투 규칙**: raw git 출력을 그대로 보여주지 않는다. 번역해서 말한다. 단 (a) 에러
원문을 사용자가 요청했을 때, (b) 브라우저 로그인 코드처럼 사용자가 *읽어서 입력해야
하는* 값은 원문 그대로 보여준다.

## 2. 마무리 카드 — 모든 git 스킬이 같은 형식으로 끝낸다

```
### 지금 상태
- {내 컴퓨터 ↔ 팀 저장소 관계 한 줄}
- {지금 있는 갈래 / 진행 중인 작업이 있는지}

### 다음에 할 수 있는 것
- {권장 다음 행동 (스킬 이름 포함)}
- {대안}
- 잘 모르겠으면: 여기서 멈추고 팀에 물어보기 — 지금 상태 그대로 두면 아무것도 망가지지 않아요
```

마지막 줄은 항상 **사실이어야 한다**. 그래서 모든 흐름은 중간에 멈춰도 이어서 할 수
있는 상태로만 남긴다. 되돌릴 수 없는 지점을 지나야 할 때는, 지나기 전에 사용자에게
먼저 확인받는다.

## 3. 에러 번역표 — 원문을 만나면 이렇게 해석하고 이 스킬로 넘긴다

| 원문에 들어 있는 말 | 실제 의미 (사용자에게) | 담당 스킬 |
|---|---|---|
| `Authentication failed` / `could not read Username` | 팀 저장소가 "너 누구야?"를 묻는데 답을 못 하고 있어요 | `github-login` |
| `Support for password authentication was removed` | GitHub은 계정 비밀번호로는 안 받아요. 컴퓨터용 출입증을 발급받아야 해요 | `github-login` |
| `403` / `Permission denied` (HTTPS) | 로그인은 됐는데 이 저장소에 쓸 권한이 없어요 (계정이 다르거나 초대 안 됨) | `github-login` |
| `Permission denied (publickey)` | SSH라는 다른 연결 방식이 설정돼 있는데 열쇠가 안 맞아요 — 이 설정을 해준 사람에게 문의 | `github-login` (에스컬레이션) |
| `Repository not found` | 주소가 틀렸거나, 비공개 저장소에 접근 권한이 없어요 | `github-login` |
| `GH006` / `protected branch` | main은 직접 올리지 못하게 잠겨 있어요 (정상) | `push` |
| `! [rejected]` / `fetch first` / `non-fast-forward` | 동료가 먼저 올린 게 있어서, 받아온 다음에 올려야 해요 | `pull` → `push` |
| `CONFLICT` / `Automatic merge failed` | 같은 곳을 두 사람이 고쳤어요. 어느 쪽을 남길지 골라야 해요 | `fix-conflict` |
| `You have unmerged paths` | 충돌 정리가 아직 안 끝난 상태예요 | `fix-conflict` |
| `detached HEAD` | 기록 열람 모드예요 — 저장해도 어느 갈래에도 붙지 않아요 | `status` |
| `not a git repository` | 이 폴더는 아직 git으로 관리되고 있지 않아요 | `status` → `welcome` |
| `no commits between` | 합칠 내용 차이가 없어요 | `pr` → `status` |

## 3.5. 프로젝트에 같은 이름의 스킬이 있을 때

이 플러그인의 스킬은 `/jay-skills:` 접두어로 불린다. 프로젝트에 같은 이름의 스킬이
따로 있으면(예: HR 패키지의 `/commit`) 접두어 없는 그 스킬이 별도로 존재한다 —
**둘 다 살아 있고 충돌하지 않는다.** 그런 프로젝트에서는 프로젝트 쪽 스킬이 그 프로젝트의
규칙(게이트·기록 관례)을 담고 있으므로 그쪽을 쓴다. 플러그인 문서가 `/jay-skills:commit`을
가리키는 것은 프로젝트 스킬이 없는 경우에도 항상 맞는 이름이기 때문이다.

## 4. `gh` (GitHub 명령 도구) 확인 순서

```bash
command -v gh          # 설치돼 있나
gh auth status         # 로그인돼 있나
```

둘 중 하나라도 실패하면 그 자리에서 진단하지 말고 이 문장으로 넘긴다:

> "GitHub 연결부터 정리해야 해요. `/jay-skills:github-login`을 먼저 실행할게요."

`gh`는 **자동 설치하지 않는다** — 설치 방법을 안내하고 스킬을 끝낸다.

## 5. 안전 기준선 — 모든 git 스킬이 지킨다

절대 하지 않는 것:

- `git push --force` / `--force-with-lease` — 어떤 상황에서도.
- `git reset --hard` / `git clean -f` — 저장 안 된 작업이 말없이 사라진다.
- 이미 올린(push한) 이력을 고치는 것 — rebase, amend, history 재작성 전부.
- `--no-verify` 로 검사 건너뛰기.
- 사용자에게 보여주지 않고 충돌 조각을 임의로 고르기 (잠금 파일 예외는 §6).
- 갈래(branch) 삭제, 보관함(stash) 비우기.
- main에 직접 올리기 (모두가 함께 쓰는 갈래라, 실수가 팀 전체에 바로 퍼진다).

합치기는 **merge만** 쓰고 rebase는 쓰지 않는다. 이유: (a) 사용자 입장에서 "합치기"라는
사건 하나로 끝나고, (b) 중단이 `git merge --abort` 한 번으로 깔끔하며, (c) merge에서는
"내 버전"과 "동료 버전" 라벨이 끝까지 뒤집히지 않는다 — rebase는 라벨이 반대로 뒤집혀
비개발자에게 설명이 불가능해진다.

## 6. 사람에게 묻지 않고 정하는 것 (기술 결정)

- 합치기 방식(merge 고정), 갈래 이름 접두어(`feature/` `fix/` `chore/`), `-u` 옵션 부착,
  base 갈래 선택, 잠금 파일(`package-lock.json`·`yarn.lock`·`pnpm-lock.yaml`) 충돌 처리.
- 잠금 파일은 동료 버전을 그대로 받고, 정했다는 사실만 알려준다 — 사람이 고를 내용이
  아니다.

## 7. 사람에게 반드시 묻는 것 (내용 결정)

- 충돌 조각마다 어느 쪽을 남길지, 저장 안 된 변경을 버릴지, 갈래 이름이 괜찮은지,
  리뷰 요청 제목·설명이 맞는지, 팀 저장소 주소.
- 추천 표시가 있어도 **자동 선택하지 않는다.** 사용자가 읽고 고르는 것이 이 도구의 목적.
