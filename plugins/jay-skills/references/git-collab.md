# git 협업 공용 참조 (jay-skills)

git 계열 스킬(`status` `github-login` `push` `pull` `fix-conflict` `undo` `pr` `review-pr`)이
공유하는 어휘·마무리 카드·에러 번역표·안전 기준선. 각 스킬은 이 표들을 복사하지 말고
필요할 때 이 파일을 읽는다 (경로: `${CLAUDE_PLUGIN_ROOT}/references/git-collab.md`,
= 플러그인 루트의 `references/git-collab.md`).

---

## 0. 이 도구들이 가정하는 팀

**개발자가 없는 팀을 가정한다.** 사용자도, 함께 일하는 동료도 비개발자다. 그래서
"개발팀이 검토해서 합쳐준다" 같은 흐름은 없다 — **확인도 merge도 팀이 직접 한다.**

여기서 나오는 결과가 두 가지다.

1. **막혔을 때 넘길 상대가 기본적으로 "팀"이다.** "개발자에게 물어보세요"라고 말하지
   않는다. 대신 (a) 지금 상태를 그대로 두고 멈추기, (b) 그 파일을 최근에 고친 동료에게
   물어보기(`git log -1 --format='%an' -- {파일}` 로 누구인지 알 수 있다), (c) 저장소를
   만든 사람에게 문의 — 셋 중 상황에 맞는 것을 제안한다.
2. **merge를 막아두지 않는다.** 아무도 합쳐주지 않으면 요청만 쌓이고 일이 진행되지
   않는다. 다만 merge는 팀 최종본을 바꾸는 일이라, 충돌이 없고 사용자가 명시로 확인했을
   때만 한다 (`pr` 스킬 Step 6, `review-pr` 스킬 Step 4).

예외 — 진짜로 기술자가 필요한 자리는 그대로 남긴다: SSH 설정처럼 누군가 세팅해 준 것,
회사 자체 GitHub 서버 주소, 저장소 권한 부여. 이때도 "개발자"가 아니라 **"그 설정을 해준
사람" / "저장소를 만든 사람"**이라고 부른다.

## 1. 어휘표 — 원어를 쓰고, 한 스킬 안에서 첫 등장 한 번만 한 줄로 풀이한다

**원칙: 핵심 용어는 원어로 쓴다.** 순한국어로 바꿔 부르면 한 낱말이 여러 뜻을 갖게 된다
— "합치기"는 merge이기도, PR이기도, 텍스트 두 조각을 이어 붙이는 것이기도 해서 사용자가
매번 되물어야 했다(실측). 원어는 GitHub 화면과 에러 메시지에 그대로 나오는 말이라, 한 번
익히면 그 화면들이 함께 읽힌다.

**풀이는 한 번이다.** 한 스킬(한 흐름) 안에서 그 용어가 처음 나올 때만 가운데 열처럼
쓰고, 같은 흐름의 그다음부터는 오른쪽 열만 쓴다. 매번 다시 풀이하면 읽기가 늘어지고,
아예 빼면 처음 만난 사용자가 막힌다.

| 용어 | 첫 등장에서 이렇게 풀이한다 | 그다음부터 |
|---|---|---|
| commit | 커밋(작업에 이름표를 붙여 내 컴퓨터에 기록하는 것) | 커밋 |
| push | push(내 커밋을 팀 저장소로 올려 동료가 볼 수 있게 하는 것) | push |
| pull | pull(동료가 팀 저장소에 올린 작업을 내 컴퓨터로 받아오는 것) | pull |
| fetch | fetch(받아오기 전에 "새 게 있나"만 확인하는 것 — 보통 사용자에게 안 보인다) | fetch |
| branch | 브랜치(다른 사람 작업을 건드리지 않고 내 작업만 따로 담아두는 공간) | 브랜치 |
| switch | switch(다른 브랜치로 옮겨 가는 것. 옛 자료나 동료의 말에는 checkout으로 나오는데 같은 일이다) | switch |
| main | main — 모두가 함께 쓰는 브랜치, 팀의 최종본. 여기에 바로 push하지 않고 확인을 거쳐 merge한다 | main |
| remote / origin | 팀 저장소(GitHub에 있는 공용 보관소, 별명이 `origin`). 주소가 `github.com`일 수도, 회사 자체 서버(`github.<회사>.com`)일 수도 있다 | 팀 저장소(origin) |
| upstream | upstream(내 브랜치가 팀 저장소의 어느 브랜치와 이어져 있는지 — 그 짝) | upstream |
| merge | merge(두 브랜치의 작업을 하나로 모으는 것) | merge |
| rebase | rebase(merge 대신 이력을 재정렬하는 방식 — 이 도구는 쓰지 않는다) | rebase |
| conflict | 충돌 — 같은 파일 같은 부분을 나와 동료가 다르게 고쳐서, 어느 쪽을 남길지 사람이 정해야 하는 상태. **고장이 아니다** | 충돌 |
| PR (Pull Request) | PR("내 작업을 main에 합쳐도 될까요"라고 동료에게 올리는 확인 요청) | PR |
| stash | stash(지금 작업을 잠깐 치워뒀다가 나중에 그대로 꺼내는 서랍) | stash |
| revert | revert(이전 커밋을 지우는 게 아니라, 반대 내용의 새 커밋을 만들어 원상복구하는 것) | revert |
| clone | clone(팀 저장소를 이력까지 통째로 복사해 오는 것 — zip 다운로드와 다르다) | clone |
| force push | 덮어쓰기(팀 저장소의 이력을 강제로 갈아치우는 것). **절대 하지 않는다** | — |

**사용자가 순한국어로 말하는 것은 그대로 알아듣는다.** "저장해줘"(커밋), "올려줘"(push),
"받아와줘"(pull), "치워둬"(stash), "되돌려줘"(revert 또는 restore)는 전부 정상 입력이다.
알아듣되 **응답은 원어로 통일**한다 — 사용자가 쓰는 말과 화면에 나오는 말을 이어 주는
것이 목적이다. "합쳐줘"처럼 여러 뜻이 가능한 말은 무엇을 뜻하는지 되물어 확정한다.

**"합치기"라고 부르지 않는 것**: 텍스트 두 조각을 이어 붙이는 일(`fix-conflict`의 "둘 다"
선택지)은 merge와 섞이므로 **"두 내용을 이어서 한 문장으로 정리"**라고 말한다.

**말투 규칙**: raw git 출력을 그대로 보여주지 않는다. 번역해서 말한다. 단 (a) 에러
원문을 사용자가 요청했을 때, (b) 브라우저 로그인 코드처럼 사용자가 *읽어서 입력해야
하는* 값은 원문 그대로 보여준다.

## 2. 마무리 카드 — git 상태를 바꾼 턴을 닫는 형식

```
### 지금 상태
- {내 컴퓨터 ↔ 팀 저장소 관계 한 줄}
- {지금 있는 브랜치 / 진행 중인 작업이 있는지}

### 다음에 할 수 있는 것
- {권장 다음 행동 (스킬 이름 포함)}
- {대안}
- 잘 모르겠으면: 여기서 멈추고 팀에 물어보기 — 지금 상태 그대로 두면 아무것도 망가지지 않아요
```

마지막 줄은 항상 **사실이어야 한다**. 그래서 모든 흐름은 중간에 멈춰도 이어서 할 수
있는 상태로만 남긴다. 되돌릴 수 없는 지점을 지나야 할 때는, 지나기 전에 사용자에게
먼저 확인받는다.

### 언제 붙이고 언제 안 붙이나

카드는 안심 장치다. 아무 데나 붙이면 안심 장치가 소음이 되고, 정작 필요한 자리에서
빠지면 사용자가 자기 작업이 어디 있는지 모른 채 끝난다. 실측에서 **양쪽 오류가 다** 났다.

- **붙인다** — git 상태가 바뀐 턴: 커밋·push·pull·merge·revert·stash 출입이 일어난 턴.
  그리고 `status` 스킬(카드 자체가 그 스킬의 산출물이다).
- **붙이지 않는다** — 읽기만 했거나 파일만 고친 턴. 필요하면 한 줄로 마무리한다.
- **스킬 본문이 카드를 의무화한 경우**(`undo`·`fix-conflict`의 마무리처럼)는 **생략하지
  않는다.** "없어진 것처럼 보이는 작업이 지금 어디 있는지"가 그 카드에만 실린다.
- 마지막 탈출구 줄("잘 모르겠으면…")은 **같은 세션의 직전 카드에 이미 나왔으면 생략할
  수 있다.** 같은 문장이 열 번 반복되면 읽히지 않는다.

## 3. 에러 번역표 — 원문을 만나면 이렇게 해석하고 이 스킬로 넘긴다

**맨 윗줄부터 본다.** 네트워크 문제를 인증 문제로 잘못 분류하면 사용자는 되지도 않을
로그인만 반복하게 된다.

| 원문에 들어 있는 말 | 실제 의미 (사용자에게) | 담당 |
|---|---|---|
| `Couldn't connect` / `Failed to connect` / `port 443` / `Connection timed out` / `Connection refused` / `i/o timeout` / `dial tcp` / `could not resolve host` / (도구가 낸) `Command timed out` | **인증 문제가 아니라 네트워크가 안 닿는 것.** 사내 저장소면 회사 VPN부터 켜야 한다 | 그 자리에서 VPN 안내 후 **정지**. `github-login`으로 보내지 않는다 |
| `Authentication failed` / `could not read Username` | 팀 저장소가 "너 누구야?"를 묻는데 답을 못 하고 있어요 | `github-login` |
| `Support for password authentication was removed` | GitHub은 계정 비밀번호로는 안 받아요. 컴퓨터용 출입증을 발급받아야 해요 | `github-login` |
| `403` / `Permission denied` (HTTPS) | 로그인은 됐는데 이 저장소에 쓸 권한이 없어요 (계정이 다르거나 초대 안 됨) | `github-login` |
| `Permission denied (publickey)` | SSH라는 다른 연결 방식이 설정돼 있는데 열쇠가 안 맞아요 — 이 설정을 해준 사람에게 문의 | `github-login` (에스컬레이션) |
| `Repository not found` | 주소가 틀렸거나, 비공개 저장소에 접근 권한이 없어요 | `github-login` |
| `GH006` / `protected branch` | main은 직접 push하지 못하게 잠겨 있어요 (정상) | `push` |
| `! [rejected]` / `fetch first` / `non-fast-forward` | 동료가 먼저 push한 게 있어서, pull한 다음에 push해야 해요 | `pull` → `push` |
| `CONFLICT` / `Automatic merge failed` | 같은 곳을 두 사람이 고쳤어요. 어느 쪽을 남길지 골라야 해요 | `fix-conflict` |
| `You have unmerged paths` | 충돌 정리가 아직 안 끝난 상태예요 | `fix-conflict` |
| `detached HEAD` | 기록 열람 모드예요 — 커밋해도 어느 브랜치에도 붙지 않아요 | `status` |
| `not a git repository` | 이 폴더는 아직 git으로 관리되고 있지 않아요 | `status` → `welcome` |
| `no commits between` | 합칠 내용 차이가 없어요 | `pr` → `status` |

**분류 순서**: 네트워크 → 권한/인증 → git 상태. 위에서 아래로 내려가며 처음 맞는 행을
쓴다. 인증 경로로 곧장 넘기는 지름길을 만들지 않는다.

## 3.5. 프로젝트에 같은 이름의 스킬이 있을 때

이 플러그인의 스킬은 `/jay-skills:` 접두어로 불린다. 프로젝트에 같은 이름의 스킬이
따로 있으면(예: HR 패키지의 `/commit`) 접두어 없는 그 스킬이 별도로 존재한다 —
**둘 다 살아 있고 충돌하지 않는다.** 그런 프로젝트에서는 프로젝트 쪽 스킬이 그 프로젝트의
규칙(게이트·기록 관례)을 담고 있으므로 그쪽을 쓴다. 플러그인 문서가 `/jay-skills:commit`을
가리키는 것은 프로젝트 스킬이 없는 경우에도 항상 맞는 이름이기 때문이다.

## 3.6. 원격(네트워크) 명령을 실행할 때

`git fetch` · `git push` · `git pull` · `gh` 계열은 회사망·VPN 상태에 따라 오래 멈춰 있을
수 있다. 실측에서 **75초 동안 아무 말 없이 기다린** 적이 있다 — 그동안 사용자는 무슨 일이
일어나는지 알 수 없었다.

1. **실행 전에 미리 말한다**: "팀 저장소 연결을 확인할게요 — 몇 초 걸릴 수 있어요."
2. **git 명령은 저속 차단을 걸어 15초 안에 끝나게 한다.** macOS에는 `timeout` 명령이 기본
   설치돼 있지 않으므로 git 자체 옵션을 쓴다:

   ```bash
   git -c http.lowSpeedLimit=1000 -c http.lowSpeedTime=15 fetch
   ```

3. `gh`에는 같은 옵션이 없다. 오래 걸리면 기다리는 중이라는 사실을 한 번 더 알리고,
   실패하면 §3 **맨 윗줄(연결 실패)**부터 분류한다.
4. 오래 걸린 끝에 실패했으면 **인증부터 의심하지 않는다.** 오래 걸렸다는 것 자체가
   네트워크 쪽 신호다.

## 4. `gh` (GitHub 명령 도구) 확인 순서

```bash
command -v gh                          # 설치돼 있나
gh auth status --hostname <목표 서버>   # 그 서버에 로그인돼 있나
```

**목표 서버는 `github.com`으로 가정하지 않는다.** 회사가 자체 GitHub 서버를 운영하면
저장소 주소가 `github.<회사>.com` 이고 그 서버와 github.com은 별개다. 목표 서버는
`git remote get-url origin` 의 호스트 부분이며, origin이 없을 때만 `github.com` 이다.
저장소 폴더 *안에서* 실행하는 `gh pr` 같은 명령은 주소를 보고 서버를 알아서 찾는다.

**판정은 `--hostname` 을 붙인 결과로만 한다.** 옵션 없는 `gh auth status`는 등록된 모든
서버를 함께 보여주기 때문에, 다른 서버에 로그인돼 있는 것을 "로그인됨"으로 오판한다.
옵션 없는 출력은 전체 그림을 보는 참고용이다.

호스트 추출은 이 형태를 쓴다(스킬마다 다르게 쓰지 않는다):

```bash
HOST=$(git remote get-url origin 2>/dev/null \
       | sed -E 's#^[a-z]+://##; s#^[^@/]*@##; s#[:/].*$##')
[ -n "$HOST" ] || HOST=github.com
```

둘 중 하나라도 실패하면 그 자리에서 진단하지 말고 이 문장으로 넘긴다:

> "GitHub 연결부터 정리해야 해요. `/jay-skills:github-login`을 먼저 실행할게요."

`gh`는 **자동 설치하지 않는다** — 설치 방법을 안내하고 스킬을 끝낸다.

## 5. 안전 기준선 — 모든 git 스킬이 지킨다

절대 하지 않는 것:

- `git push --force` / `--force-with-lease` — 어떤 상황에서도.
- `git reset --hard` / `git clean -f` — 커밋 안 된 작업이 말없이 사라진다.
- 이미 push한 이력을 고치는 것 — rebase, amend, history 재작성 전부.
- `--no-verify` 로 검사 건너뛰기.
- 사용자에게 보여주지 않고 충돌 조각을 임의로 고르기 (잠금 파일 예외는 §6).
- 브랜치 삭제, stash 비우기.
- main에 직접 push하기 (모두가 함께 쓰는 브랜치라, 실수가 팀 전체에 바로 퍼진다).
- **사용자가 요청하지 않은 커밋.** "정리해줘" / "오늘 여기까지 할게요" 같은 마무리
  요청도 커밋 요청이 아니다. 커밋 안 된 변경이 있으면 **그 사실만 알리고 커밋할지
  물어본다.** 실측에서 마무리 요청을 커밋 요청으로 읽고 `git add -A && git commit`을
  말없이 실행한 적이 있다 — 사용자는 그 커밋에 무엇이 들어갔는지 고를 기회를 잃었다.

merge에는 **merge만** 쓰고 rebase는 쓰지 않는다. 이유: (a) 사용자 입장에서 한 사건으로
끝나고, (b) 중단이 `git merge --abort` 한 번으로 깔끔하며, (c) merge에서는 "내 버전"과
"동료 버전" 라벨이 끝까지 뒤집히지 않는다 — rebase는 라벨이 반대로 뒤집혀 비개발자에게
설명이 불가능해진다.

## 6. 사람에게 묻지 않고 정하는 것 (기술 결정)

- merge 방식(merge 고정), 브랜치 이름 접두어(`feature/` `fix/` `chore/`), `-u` 옵션 부착,
  base 브랜치 선택, 잠금 파일(`package-lock.json`·`yarn.lock`·`pnpm-lock.yaml`) 충돌 처리.
- 잠금 파일은 동료 버전을 그대로 받고, 정했다는 사실만 알려준다 — 사람이 고를 내용이
  아니다.
- **브랜치 이름은 영문 소문자와 하이픈만 쓴다** — `feature/security-training-notice`.
  브랜치 이름은 GitHub 주소에 그대로 들어가는데, 한글이 섞이면 주소가
  `%ED%95%9C%EA%B8%80` 같은 알아볼 수 없는 형태로 바뀐다(실측). 작업 내용이 한국어면 그
  뜻을 영문으로 옮겨 짓고, 사용자에게는 한 줄로만 알린다: "브랜치 이름은 주소에 들어가서
  영문으로 지어요."

## 7. 사람에게 반드시 묻는 것 (내용 결정)

- 충돌 조각마다 어느 쪽을 남길지, 커밋 안 된 변경을 버릴지, 브랜치 이름이 괜찮은지,
  PR 제목·설명이 맞는지, 팀 저장소 주소.
- 추천 표시가 있어도 **자동 선택하지 않는다.** 사용자가 읽고 고르는 것이 이 도구의 목적.
- **질문과 선택지 문구는 제출 전에 한 번 다시 읽는다.** 사용자가 고르기 전 반드시 읽는
  화면이라, 오타·조사 오류·자모 깨짐이 남으면 뜻이 흐려지고 신뢰가 깎인다. 실측에서 한
  세션에 7건이 누적됐다("둔까요", "리대로", "널 갈래에").
